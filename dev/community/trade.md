## 定案與理由

| 決定 | 為什麼 |
|---|---|
| 開單、領收、取消、封存都經 `TradeService`，「誰是需求方」只寫一處（10-03，A＋B） | 原本接單和領收各寫一次，靠從訊息文字切字串 |
| 角色叫需求方、供應方，不叫買家、賣家；11-06 起介面也不再用「上架者」 | 交易不一定是買賣；群友只要認需求方、供應方兩個詞 |
| 所有自己發的貼文都能接單，只有對貼文本身按的表情才算（TR-Q2） | 標題沒辦法規定使用者怎麼打，沒人按表情就不會發動；供應方對貼文裡別人的回覆按 ✅ 表示收到很常見 |
| 同一篇需求，每位供應方各開一個私人交易對話；一位完成後其他對話結束、需求貼文刪掉（TR-Q8） | 不同供應方接同一篇很正常；完成就刪貼文，代表一篇需求只成交一次，要分給多人就各發一篇 |
| 需求方按「還沒領收」就暫停倒數，到期前 6 小時提醒一次（TR-Q18） | 自動領收是怕需求方忘了按；保護需求方靠「說沒收到就停」和到期前提醒 |
| 取消只有供應方和群主能按，有已收的款先跳確認；需求方要取消就跟供應方說（TR-Q4、Q57） | 需求方受領服務後擅自取消會有糾紛；群主也能取消，供應方不在時才不會卡死 |
| 商品用按鈕跳表單、bot 代發貼文，入口在論壇置頂的「上架說明」（TR-Q6、Q13） | 之後要做多品項，原生發文很難做到；不增加指令數 |
| 同一系列放同一篇，買家用下拉挑品項（TR-Q14） | 分篇的話，批次上架的圖要對到哪一篇，照順序對很容易錯 |
| 價格只填數字，幣別每篇設一次（TR-Q23） | 下單明細要算小計，自由文字算不出來 |
| 下單就預留數量、取消還回；填完數量先看明細再「確認下單」（TR-Q16、Q20） | 預購要避免超賣；買家手滑就得找供應方取消 |
| 商品貼文只放一顆灰色「⚙️ 管理商品」，沒權限的人按了被拒（TR-Q21、Q24） | 一則訊息最多 5 列元件；使用者第一次實測就按到貼文卡片、沒聽過右鍵選單，觀星者也會找不到 |
| 編輯時數量填「剩餘數量」（TR-Q27） | 原本是含已賣出的總數，補貨容易填錯（賣光 3 個再補 5 個要填 8） |
| 交易結束馬上鎖定封存，並私訊雙方附對話連結（TR-Q29） | 通知其實有發，但發完 1 秒就封存，對話從列表消失，提及標記跟著看不到 |
| 市集留底只記每筆下單與交易對話連結，不附對話內容（TR-Q44、Q45） | 私人交易對話本身就是備份 |
| 每一項叫「品項」，程式仍叫 `Variant`（TR-Q30、Q31） | 「品相」一般指物品的成色；改變數名只會讓 diff 變大 |
| 不能買的品項加刪除線＋灰底標籤，選單把狀態放最前面（TR-Q38） | embed 文字不能改顏色，有顏色的 ansi 區塊手機上不顯示；手機上選單說明被截斷也看得到狀態 |
| 下架不真的刪除：停止接單、保留紀錄、不能恢復；暫停販售改剩餘 0（TR-Q39） | 交易對話、留底、預購提醒、取消還回都要讀商品貼文 |
| 定金與尾款是同一個品項的兩筆錢，在同一個交易對話收完，尾款由 bot 在原對話通知付（TR-Q46） | 兩份對照程式的審查都建議這個做法；放同一篇，需求方在同一篇就看得到 |
| 同一位需求方、同一篇商品一個交易對話；每個品項各自按「已交付」，那個品項的錢收齊才能按（TR-Q56、Q55） | 品項可能不同時間交付、通常一起付款；最大的坑是收定金時照習慣按通知領收，需求方一領收整串結束、尾款找不到對話 |
| 一次付清的品項也要確認「已收到款項」（TR-Q61） | 寄出到需求方收到之間有時間差 |
| 交付分數位與實體，每篇商品設一次；新上架預設實體（TR-Q64、Q65） | 數位選成實體頂多多按一次「已收到」，實體選成數位會 24 小時自動完成 |
| 實體寄出第 7 天起每 3 天 @ 雙方，直到收到或取消，不拉群主、不自動完成（TR-Q66，沒照建議） | 就是要逼雙方追蹤，不然就取消交易 |
| 定金品項一定要填截止，開始收尾款後自動停收；定金截止只停收定金，不說可以交貨（TR-Q59、Q69） | 不靠「剩餘 0」停賣，取消還回才不會重新開賣；定金截止時貨還在路上 |
| 交易正本放資料庫，商品、品項也一起搬，交易對話裡的訊息從資料庫畫（TR-Q74、Q76，推翻 TR-Q1） | Discord 當紀錄要繞路：翻全部封存對話才列得出某人的交易、30 天範圍漏掉等貨交易、結束後讀不到身分、對話被刪紀錄就沒、custom_id 放不下以後的金流序號、提醒次數與週報去重沒地方記 |
| 開新的 SQLite 檔 `src/services/market.db`（TR-Q75） | discord-bot 容器只掛 `./src` 與 `./logs`，新檔要放在 src 底下 |
| 每天備份一個檔 `market_YYYY-MM-DD.db`，留 14 份，放在資料庫旁的 `market_backup/` | 打包成一個 zip 壞一次 14 天全沒；放同一個掛載點，換名才不會跨 mount 失敗 |
| 還有沒收完尾款或沒交貨的定金、預購交易時不能下架 | 下架後管理面板按不了，延期、開始收尾款、開始交貨都按不到 |
| 開發放在另一個資料夾的分支（`git worktree`） | bot 直接跑主目錄的程式，改動很大，匯入做一半上線會出事 |
| 交易中不能改幣別 | 金額存數字、幣別在商品上，改了已收的錢會整批換成新幣別顯示 |
| 交易對話被刪就記成取消 | 原本會永遠算進行中：份數一直佔著，擋著刪品項與下架 |
| 不支援上線後退回舊版（TR-Q78） | 退版期間舊程式發的貼文、開的對話不會進資料庫，回新版會被當成做到一半而刪掉或鎖起來；寫進上線清單就好，不用多寫程式 |
| 被拿掉觀星者身份組的人，商品不接新訂單，進行中的照常做完（TR-Q79） | 拿掉身份組多半就是不讓這個人繼續賣 |
| 舊交易直接掛上新類型、補送交易進度且不 @ 人（TR-Q80） | 舊資料都還停在未付定金的狀態 |
| 「💰 改成定金＋尾款」先保留、之後拿掉 | 有兩篇各兩個品項，一個一個改會被「定金不能跟一次付清放同一篇」（TR-Q60）擋下 |
| 銜接程式獨立成 `market_transition`，用 switches.json 開關，5 篇都改好才關（TR-Q82～Q84） | 5 篇改好後這些規則本來就不會再觸發；關掉就照一般規則，可以下單、舊交易照舊流程完成 |

## 踩過的坑

- **編輯商品貼文時回傳空的 `attachments` 會把圖刪掉**：被 embed 引用的圖（`attachment://檔名`）不在 `attachments` 清單裡。更新貼文只傳 `embed=`，要換圖才重新上傳。
- **結束時先鎖定封存再發訊息，對話會被重新打開**：改成先發訊息再鎖定封存。
- **用「標題含來源 ID」判斷重複開單**：第二位供應方的通知被塞進第一位的對話，第二位本人看不到。改用來源貼文＋供應方判斷。
- **排程最多睡 1 小時，途中改截止時間不會知道**：10-04 改成 22:50 的截止，要到約 23:30 才提醒。`run_due_loop` 加 `wake`，改了就提早醒來重算。
- **discord.py 2.7.1 的上傳欄位照附件表排序，不照選取順序**：商品大圖變成最後選的那張。改成從 `interaction.data` 讀選取順序重排；方向是照症狀推測的，要用標了 1、2、3 的圖實測確認。
- **私人對話最長 7 天自動封存**：等貨的交易大部分時間是封存的，用 30 天範圍掃會漏掉，要靠 `archived_threads(private=True)` 找。
- **舊的品項格式欄數不對，品項會默默消失**：`Variant.decode` 欄數不是 6 就回 None，下一次存檔那個品項連同已下單數量就永久不見。
- **啟動 gate 裡判斷不到測試模式**：gate 先 import `test` 套件才 import unittest，`"unittest" in sys.modules` 是 False，市集資料庫沒換成暫存檔，合併後 bot 會起不來（在分支複本重現 96 項 FAILED）。改成 `_is_test_run` 也認 `sys.orig_argv`；GPU 鎖檔、`RUNTIME_BACKUP_DIR` 是同一個舊問題，一起修。
- **測試沒照真按鈕的路走，版本比對寫反沒抓到**：按鈕帶的卡片版本永遠「等於」最後一筆錢，判斷寫成「大於」，所有「我已付」都不算數。測試原本直接呼叫 `handle_step` 不帶版本，改成跟真按鈕一樣讀卡片上的版本再送。
- **測試用的假 Discord 少了真實規則**：封存中的 thread 要在同一個請求裡解封才改得了（50083）、封存中加不了人、訊息最多 2000 字。少了這三條，中度問題一直抓不到。
- **拿著交易鎖去重畫商品貼文，會跟截止通知互等卡死**：卡住時所有截止與自動完成都停到重啟。改成放開交易鎖之後再重畫；鎖的順序一律商品鎖 → 開單鎖 → 交易鎖。
- **論壇貼文改名每 10 分鐘只能 2 次**：撞到時 discord.py 會睡九分多鐘（11-05 正式 log 有一次 429 retry 540 秒），面板一直卡在「處理中」。改名移到背景，照資料庫同步。
- **`Thread.edit` 回傳新物件、不改手上那份**：剛被封存回去的貼文，手上那份看不出來。`reopen_thread(force=True)` 一律送一次解封。
- **舊交易一轉過來就被催款**：催款起點是十月的下單時間，一轉換一分鐘內就 @「第 1 次提醒」。改成從轉換那一刻（`adopted` 事件）起算；演練又發現第一天就被算成超過 14 天沒動靜，`adopted` 也改成算動靜。

- **TR-Q7（已定案＝C，原選項保留供追溯）舊的固定物品價格表（10-03 使用者重新問：價目表和上架商品要分開還是合併，看起來是兩個模組）**：兩者都在回答「這位供應方賣什麼、多少錢」。A＝分開：價目表照舊（自由市場接單時附上），上架商品另一套；零遷移，但供應方兩邊維護、買家看到兩套價格。B＝現在就合併：每位供應方的價目表變成商品論壇裡一篇「代儲價目」商品（品相＝固定品項、立即購買），`/set_item_prices` 改成編輯那篇，接單時附的價目表從那篇讀；要搬 `item_prices.json`（2 位供應方，先備份、取得同意）。C＝設計上合併、分兩階段做：先做商品上架，商品目錄一開始就按「價目表也是一種商品」設計；上架穩定後再把價目表搬進去、停用舊指令。**建議 C**（架構檢視候選 C「商品目錄」的方向，不卡住上架）。順帶：價目表裡價格 0 的品項也會列出來（例：6480 月相 價格 0），是否代表不賣、要不要隱藏，待使用者說明。

- **TR-Q6 上架 UI**：Modal 最多 5 個欄位、不能動態增減、也不能預覽，多品相塞不進一張；只用 embed＋按鈕又沒有文字輸入。**建議混合式**：上架面板用 embed 預覽整個商品，按鈕「新增品相」跳出一品相一張的 modal，類型（預購／立即購買）在 modal 裡用下拉選（印象 modal 已經這樣用）；另有「編輯／刪除品相」（先下拉選品相）和「發布」。商品貼文用「選擇品相」下拉加購買，比一個品相一顆按鈕好擴充。草稿和已發布的品相都存在 bot 自己的 embed 裡（和 TR-Q1 B 一致）。這種一品相一張 modal 的做法不需要候選 D。
