## 定案與理由

| 決定 | 為什麼 |
|---|---|
| FB 改成 scraper 抓完推送通知，拿掉 bot 輪詢；圖片全量替換 | 輪詢有時間差，FB CDN 網址的 token 會過期，又沒有刷新機制 |
| 共用層的瀏覽器池只用 Firefox 系（firefox144／147＋30% 本機 Firefox ESR） | 所有網站都通過的只有 Firefox 系；一個 IP 固定用同一種瀏覽器，也比每次換一種像真人 |
| 共用層加 `run_session()`，HKEPC、PTT、官網的一輪都共用一個 session | 使用者：不容易被擋的做法應該大家一起共用；以前 HKEPC 每頁換瀏覽器、cookie 不延續 |
| 拿掉自己加的 `Sec-CH-UA` 系列標頭（SC-Q1） | 跟 UA 自相矛盾，是防火牆容易抓的特徵；讓 curl_cffi 送內建值，以後新增目標也會自動正確 |
| 巴哈完成那行記本輪請求數、等待秒數、頁數，不開逐筆 log（SC-Q4） | 下一輪就知道時間花在哪；逐筆 log 太多 |
| curl_cffi 的 `BrowserType` 改成可選匯入 | 原始碼標成 1.x 移除，requirements 不鎖版本，拿不到會啟動失敗 |
| FB 走 IPv6：`scraper` 多接一張專用網路，`discord-net` 不動（FB-Q1 A） | 只要重啟 `scraper`；`discord-net` 開 IPv6 要所有容器重建，`network_mode: host` 會叫不到 `discord-bot:5000` |
| Firefox 設 `network.dns.preferIPv6` | 系統排序對 FB 是 IPv4 優先，不設不會走 IPv6 |
| 主機先跑 `prepare_host_ipv6.sh` 設 `accept_ra=2` | Docker 開 IPv6 網路會把 forwarding 改成 1，核心不再收路由器通告，主機的 IPv6 到期後會斷 |
| 登入對話框偵測到才關；先按有密碼欄那個對話框的關閉鈕 | `close_login_wall` 會關任何對話框，貼文頁本身就有一個顯示貼文的對話框 |
| 已存張數符合頁面就不開照片頁；網址確認過就不開貼文頁（`confirmed_urls`） | 使用者要求「圖片數量與頁面表示數量符合就不打」；正常輪次從 4 頁降到 1 頁 |
| 內容雜湊相同且發文時間相同，才當同一篇合併（FB-Q10 A，`_is_same_post`） | 雜湊只看正規化文字、連 hashtag 都拿掉，不同貼文會撞；發文時間到秒，換 pfbid 也不變；讀不到時退回只補網址，方向安全 |
| 合併邏輯其餘維持原樣，FB-Q16 盤點出的修改都不做 | 使用者：沒說要改的地方就不用改 |
| 影片檔直接傳上 Discord、一律高畫質 | 最接近原文 |
| 不存影片、不加表；影片貼文與 `/resend_article` 都讓爬蟲重開文章拿新網址 | 檔案網址約 4.4 天過期，文章網址不會，舊到 2025-12 的貼文也重開得到；資料庫已有文章網址 |
| 影片只讀主貼文自己的附件，不整頁搜尋 | 頁面裡也有留言和別篇的影片 |
| 主文一送出就記已送，圖片與影片失敗只記 log | 原本最後才記已送，影片失敗會讓主文每小時重發 |
| 先寫資料庫，成功才寫 JSON 與確認紀錄（FB-Q20） | 否則寫資料庫失敗的新貼文，下一輪會被記成已確認，永遠進不了資料庫 |
| 退化成新增前，先用兩個網址找既有列，發文時間也相同才更新那一列（FB-Q22 B） | 修根源；不比時間的話，別篇會蓋掉原本那列 |
| FB 每小時 :05 固定抓；0 連結 20 分鐘後補抓，每輪最多 2 次 | 79% 的貼文在 :00～:04 發；重啟不換時間；用次數不靠時間湊，免得補抓和正點排程疊在一起 |
| 爬蟲的 FB 測試不放進 repo（FB-Q4） | 使用者：FB 一改就全壞，自己程式碼確認的才有意義 |
| 不藏 headless／自動化特徵，不做「看起來像人」的動作 | 那是偽裝成真人來繞過檢查；而且轉址發生在 JavaScript 跑之前，藏了也沒用 |
| 重撥 PPPoE 換 IPv4 先不做（FB-Q6） | 路由器重撥會斷整條線路；IPv6 被限制才回來看 |

## 踩過的坑

- **HKEPC 的 403 時有時無，是因為每頁隨機換瀏覽器**：它的 Cloudflare 一律擋 Chrome／Safari、Firefox 全過，抽到哪種看運氣。所以只改成「一輪一個 session」會更糟，抽到 Chrome 整輪都被擋。
- **頁面有 `challenge-platform` 不代表被擋**：Cloudflare 在正常頁面也嵌這段腳本，要認「403／503＋Just a moment」。
- **FB 把 IPv4 導去登入頁，第一個回應就轉址**：跟程式、版本、自動化特徵無關，同一個瀏覽器走 IPv6 就開得到。0 個連結只寫 log，斷了約 31 小時才被人工發現。
- **Python `urllib` 預設走 IPv4**：它印的 IP 沒有冒號是正常的，不能拿來判斷有沒有走 IPv6，要用瀏覽器開 Cloudflare trace。
- **`navigator.webdriver` 實測是 `true`**：`setup_driver` 裡的 `dom.webdriver.enabled=False` 沒有作用。
- **登入對話框晚幾秒才跳**：只在開頁後關一次會漏，翻照片時看到就判定被擋。按第一個找到的關閉鈕，會關到被蓋住的貼文那層。
- **pfbid 會一直換**：909 篇出現過 2,089 個連結。換了就走內容比對分支，原本那裡只補網址，補抓到的圖存不回去。
- **內容雜湊連 hashtag 都拿掉**：空文字和只有 hashtag 的貼文雜湊相同，換封面的貼文每次也相同，不能單靠雜湊認同一篇。
- **影片封面被當成圖片送**：926 的影片前 2 秒是白畫面，封面就是白的。整頁搜尋影片網址會抓到留言和別篇；有的貼文另有 1 秒的小片段，要核對長度。
- **FB 圖片檔案網址約 4.4 天過期（回 403）**：重發舊貼文實際上只剩文字；文章網址和貼文編號不會過期，重開就能拿到新網址。
- **分享貼文會讀成內層文字**：程式取最長的訊息容器。獲獎名單分享的是前瞻通訊，內層較長，9 篇從沒轉發，網址還補進前瞻通訊那一列（Q16-1，沒修）。
- **上傳影片時連線中斷不是 `HTTPException`**：discord.py 在 Linux 不重試（只認 errno 54／10054，Linux 是 104），原本會連標準畫質和連結都跳過。
- **`DatabaseManager.commit()` 失敗不丟例外，只回 False**：要看回傳值，不然鎖住時照樣寫 JSON。
- **只重啟 `discord-bot`、沒重啟 `scraper`**：新 API 回 404，`/resend_article` 又送了一次白圖。兩個要連著重啟。
- **測試把假紀錄寫進正式 log**：清理時的 `logging.disable(NOTSET)` 會把 log 打開，載入 `main` 也會接上正式 log。改壞「沒放鎖」會讓測試卡死，要用 `timeout -s KILL` 限時。
- **`schedule.every(1).hours` 從啟動時算**：每次重啟就換時間；補抓從上一次跑完起算、主迴圈每 60 秒才檢查，時間會飄，第三次補抓會和正點排程疊在一起。
- **Firefox 沒鎖版本**：重建映像要 `--no-cache` 才會更新。

- **有隨機化**（`base_scraper_client.py`）：每個 session 從 10 個瀏覽器目標隨機選一個（Chrome 124／131／136、Edge 99／101、Firefox 133／135／144、Safari 17.0／18.0），另有 30% 機率用本地抓的 Firefox ESR 140 指紋；延遲也是隨機（巴哈每頁 2～5 秒、每篇 0.35～0.9 秒、留言 0.15～0.35 秒）。
- **查到的問題**（對 httpbin 實測送出的標頭）：
  1. **標頭自相矛盾**：`_build_page_headers`／`_build_xhr_headers` 對所有 Chromium 目標一律加 `Sec-CH-UA-Platform: "Linux"`，但 curl_cffi 的 Chrome 目標 UA 是 macOS、Edge 是 Windows；自己寫的 `Sec-CH-UA` 還蓋掉了 curl_cffi 內建的正確值（例：chrome131 內建送 `"Google Chrome";v="131", "Chromium";v="131", "Not_A Brand";v="24"`、平台 `"macOS"`，被換成 `"Chromium";v="131", "Not;A=Brand";v="24", …`、平台 `"Linux"`）。真的瀏覽器不會這樣，是防火牆很容易抓到的特徵。
  2. **HKEPC 每一頁都開新 session**（`hkepc_scraper_service.py` `_fetch_html`）：每頁隨機換一個瀏覽器、cookie 不延續，同一個 IP 幾秒內從 Mac Chrome 變 Windows Edge 變 Firefox。巴哈是一輪共用一個 session，沒有這個問題。
  3. **瀏覽器版本偏舊**：Edge 99／101 是 2022 年的版本，其他也是 2024～2025 年；2026 年的真實流量裡很少見。
  4. **403 當輪不重試**：`_fetch_with_retry` 只在連線例外時重試，拿到 403 直接交回，要等下一小時。
- **巴哈變慢另案**（見盤點紀錄 22:5x）：取樣 22:34 那輪執行緒 300 次，70% 在刻意的睡眠、21% 等網路、7% 跑 CPU，所以不是被擋或網路慢；請求一次只要 0.2 秒、每輪存的樓數也沒變，卻多花 4 倍時間（兩輪都是抓 74 分鐘＋寫 4 分鐘），原因還沒找到；每輪都比排程間隔長，每小時會有約 18 分鐘兩輪同時在抓。巴哈 logger 等級是 WARNING（`scraper/config.py`），逐筆請求不會寫 log，目前數不到每輪發了幾次請求。
