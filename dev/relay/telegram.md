## 定案與理由

| 決定 | 為什麼 |
|---|---|
| 轉發訊息用「轉發來源」比對白名單 | 以前拿目標頻道去比，轉發很容易被放行 |
| 即時 NOTIFY 之外，每小時補償輪詢，啟動時也補 | 防漏；NOTIFY 即發即棄，LISTEN 建立前發的會丟，由啟動補償撿回 |
| 媒體檔名依 photo／document id 固定 | Telethon 預設用時間戳命名，重啟重跑歷史會產生 `(N)` 重複檔 |
| 自訂表情上傳成 Discord App Emoji，只做靜態 | bot 專屬、不佔伺服器 50 格、成員表情選單看不到、程式能自己建立和刪除；動態的維持一般 emoji，不會變差 |
| footer 加資料庫編號 `db#` | Telegram 訊息編號是每個頻道各自編號，不是全域唯一 |
| 舊訊息的表情不批次回填，改由 `/resend_article` 單則重抓 | `document_id` 以前沒存，舊訊息要重掃才有 |
| 重抓交給爬蟲常駐的 client，bot 端不另開 | 另開 client 會撞 session 的 SQLite 鎖 |
| 互相轉發的去重放在爬蟲端 | 資料庫不存轉發來源，只有爬蟲處理時看得到 `fwd_from` |
| 補掃往回看 300 則，`limit` 跟著加到 500 | 只看最大 id 之後的話中段缺口永遠掃不到；使用者要改善既有流程、不另開補洞路徑；`limit` 算撈回幾則，200 會被已存在的訊息吃光 |
| 補掃間隔用程式預設 15 分鐘，不改 `runtime_config.json` | 那個檔執行中會被白名單功能自己寫入 |
| 全域鎖改成單則訊息鎖 | 同一則仍互斥（原本加鎖的目的），不同訊息恢復並行，相簿各張不再排隊 |
| 相簿補圖時效 12 小時；8/02～9/27 的舊缺圖（約 155 張）不補 | 重啟會把全部沒紀錄的舊組員排回來，沒有時效會一口氣倒進頻道；使用者只要求補當天 |
| 用模型判斷，不用關鍵字 | 含「水」的 85 則只有約 10 則是灌水；5 字以內的多半是有情報的圖說 |
| 拿不準就放行 | 頻道價值在爆料，錯放一則水代價小，錯關一則情報代價大 |
| 一定要看圖，純圖不能一律放行；跟遊戲無關的圖也算垃圾 | 反例 13649：文字只有「水」，圖是角色設計稿；使用者要擋的包含奶龍這種梗圖 |
| GIF、影片抽幀沿用 `extract_key_frames` 的挑幀規則 | 使用者要求不要重複造輪子，挑幀規則只留一份 |
| 用主模型關思考，不另用審核模型 | Lemonade 一次只放一個大模型，兩個會互相擠出 |
| 不建新表，發送紀錄記三種去向：主頻道、隔離 thread、頻道 0 | 使用者質疑隔離了就在 thread 裡，不需要表；其他讀取點都指定頻道，多一種頻道 0 不影響 |
| 頻道 0 是「停止主動追蹤」，只記不會再變的決定，還在等圖的不記 | 9/28 舊程式先把整本相簿記成已送，晚下載的圖就永遠不送；使用者指出「永遠不送」和「圖到了照樣補送」矛盾 |
| 373 則舊帳現在就標頻道 0 | 現有程式只有啟動補償不分頻道，標了重啟就不再重判 |
| 沒有路由不記成不送 | 設定檔讀不到時也會當成沒有路由，記了會靜默丟訊息 |
| 「圖晚到」的時限維持 12 小時 | 使用者怕漏掉很久才下載到的圖；查到 3 張晚了 26～43 小時 |
| Telethon 不釘版本 | 只用公開的 `get_dialogs()`；原本釘版本是為了沒做的缺口追蹤 |
| 有文字的單則最多等圖 30 分鐘，等待放在爬蟲（下載失敗先不通知） | 使用者要完整，先送文字再補圖等於切成兩篇；轉發端單則根本不等圖，放轉發端要等那批一起上線 |
| 放回走轉發原本的發送流程，不走 `/resend_article` | 那條路不合併相簿、也不寫發送紀錄 |
| 放回面板是 thread 置底的雙層選單（先選日期、再選訊息），選了先跳只有自己看得到的確認 | 使用者自訂，選單只列被隔離的、照時間排就認得出來；避免選錯就公開送出 |
| 隔離 thread 記在 runtime 檔，不用「不在路由、也不是 0」判斷 | 主頻道一改綁，4,400 筆主頻道紀錄會全被當成隔離 |
| 功能開關放新的 `settings/switches.json`，不做開關指令 | 每則重讀、改了就生效；使用者有需要就自己改檔；`config.json` 整份覆寫，手改會被舊快取蓋掉 |
| `config.json` 寫入改成重讀後只改那個 key，安全寫入加備份 | 手改後 5 分鐘內有人從 Discord 存設定，會用舊快取整份寫回 |
| 搬舊垃圾只改那列的 `discord_channel_id`，`delivered_at` 不動，不另外備份 | 比記一筆刪一筆單純；相簿補圖看第一次送出多久；Telegram 可以重抓，log 逐筆記 `db#` 與列 `id` 可照著改回 |
| 搬移順序：貼進 thread → 刪主頻道原貼文 → 改資料庫 | 刪失敗就不改，否則面板會列出來，放回後主頻道變兩份 |
| 等模型改成排隊，滿 30 分鐘才放行 | 一張圖等 90 秒就被放行，當時插話佔著模型；使用者要求排隊 |
| 沒經模型判就放行的，在發送紀錄加 `needs_recheck` 欄補判 | 使用者要每則都檢查過；和寫紀錄同一句，不會送出了標記卻沒寫上 |
| 點名別款遊戲的直接隔離，名單放 `settings/telegram_other_games.json`，比完整單字 | prompt 沒列名字，模型把別款遊戲的爆料當爆料放行；`nte` 不分字界有 38 個單位出現在英文單字裡 |
| 右鍵搬相簿不等 12 小時 | 使用者實測被擋後要馬上搬；右鍵就在負責補圖的行程裡，可以先擋住這本再搬 |
| 下載先寫 `.part` 暫存檔、完成才換名；已存在且大小符合就不重下 | 同 id 重下時 Telethon 當場清空舊檔再寫，中斷就壞掉 |

## 踩過的坑

- **Telethon 會漏派新訊息事件**：handler 完全沒被呼叫。只靠即時事件的話漏了就永久漏，7/25 有 28/63 則靠重啟才補進來。要有定期補掃。
- **啟動時沒讀對話清單，相簿常缺開頭**：Telethon 把啟動後第一個推送當起點，比它早的當已處理丟掉；啟動後第一則漏收 53%。啟動時先 `get_dialogs`。
- **一把全域鎖會讓相簿漏圖**：Telethon 預設並行派發，全域鎖把同時到的相簿各張變成排隊，轉發端等不到整組就先發，晚到的被丟掉。鎖要以單則訊息為單位。
- **「決定不送」只記在記憶體**：重啟後啟動補償把沒紀錄的都當成沒處理，每次重啟都重判；測試還把「過時效不寫紀錄」寫成斷言，所以一直沒被抓到。
- **頻道 0 的 `delivered_at` 是標記時間**：不分頻道讀送出時間或計數時，要加 `discord_channel_id <> 0`。
- **防雷旗標讀錯欄位**：`message.media_unread` 是「媒體還沒看過」，真正的旗標在 media 物件的 `spoiler`；2,696 筆全是 false。已送出的舊訊息補不回打碼。
- **同 id 的檔重新下載會寫壞舊檔**：`need_download` 只看有沒有媒體列；10-28 補掃中斷，一支 561.8 MB 的影片只剩 360.4 MB。
- **媒體列不能刪**：刪了爬蟲重啟或補掃會重新下載；檔名依 id，同一個檔可能被好幾則共用，刪檔前要查。
- **測試的 logger 寫進正式 log**：用真實 grouped_id 跑測試，在 `discord_bot.log` 留下假的合併紀錄。測試一律用假 id。
- **被拒絕的 `docker exec` 行程還在跑**：10-07 預覽被拒絕，容器裡的行程佔著跨行程 GPU 鎖約 17 分鐘，插話和搬移都卡住。中斷後要查 `/proc/*/cmdline` 清掉。
- **用字串切到下一個 `def` 來刪函式**：連後面三個類別（其中一個只刪到前半）一起刪掉，單元測試沒紅，`test_import_resolution` 才抓到。刪函式用 AST 找起訖行號。
- **樣本原文寫進 prompt 例句，分數會虛高**：第 1 輪「誤關 0」有這個成分，例句改掉後「Soon」「32天」這類極短訊息被當成灌水。
- **模型會照抄 prompt 結尾的範例**：一張更新公告圖被判「每日打卡灌水」，結尾範例改成放行的。
- **上線不等於開關打開**：10-07 上線後 `telegram_filter_mode` 一直是 off，內鬼頻道完全沒過濾。
- **ffmpeg 直接輸出 APNG 到管線是無效檔**；fps 濾鏡會丟最後一幀，約 9% 短片一張都抽不出，要加 `eof_action=pass`。
- **GPU 鎖不可重入**：`chat_raw` 裡面已經拿鎖，外面再包一層會死鎖。
- **固定等一段時間的測試，啟動時會失敗**：bot 啟動時 CPU 忙，一個固定等 0.5 秒的測試沒等到，容器多重啟一次。改成等到條件成立、設上限。
- **突變測試的複本讀到正式名單**：名單類突變第一輪沒紅，要設 `APP_ROOT` 指向複本。
- **手動註冊到單一伺服器的指令不會自動清掉**：bot 啟動只同步全域指令，用完要自己刪。

**目標**：把 Telegram Premium 自訂表情（內嵌在文字裡的角色貼圖）relay 到 Discord 時還原成實際圖案，而非只剩 fallback 一般 emoji。

### 定案（2026-07-25，使用者確認）

   - 用 `GetCustomEmojiDocumentsRequest(document_id=[...])` 取 document → 下載表情檔到共用 media 目錄（重用現有跨容器穩定檔名機制）；靜態 mime = `image/webp`。
2. **對照表**（telegram_data DB，新表）：
   `telegram_custom_emoji_map(document_id BIGINT PK, discord_emoji_id BIGINT, discord_emoji_name TEXT, animated BOOL, status TEXT, file_rel_path TEXT, created_at, last_used_at)`；status = ok / failed / unsupported（動態）。

   - **與 spoiler 合併成同一次「由後往前」UTF-16 rewrite**，避免兩種 entity 並存時 offset 位移。
